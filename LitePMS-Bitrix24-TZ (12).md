# Техническое задание

## Интеграция системы бронирования LitePMS с лидами Bitrix24 (CRM — рабочая воронка, статусы — обратно в LitePMS)

**Версия:** 1.4 (гибридная схема: воронку ведёт Bitrix24, статусы передаются в LitePMS при достижении пороговых стадий)
**Дата:** 30 сентября 2026
**Заказчик:** Дмитрий Суменков (администратор портала)
**Исполнитель:** BitrixGPT 5.6 Agent 1M

---

## 1. Цель и назначение

Создать приложение (интеграционный адаптер), которое связывает систему бронирования **LitePMS** и модуль **CRM (лиды) Bitrix24** по **гибридной схеме**:

- **LitePMS — броневая/учётная система (PMS):** хранит и обрабатывает бронирования, даты, финансы, гостей, источники. Именно LitePMS — «движок» бронирования.
- **Bitrix24 — рабочая воронка продаж:** обе воронки (**B2B** и **B2C**) ведутся прямо в CRM на **лидах**. Сотрудники работают по воронке в Bitrix24; движение по стадиям и обработка заявок происходят здесь.
- **Обратная связь статуса:** при достижении **пороговых стадий** воронки адаптер передаёт статус обратно в LitePMS (метод `POST /updateBooking` → `status_id`), чтобы статус брони в PMS соответствовал продвижению в CRM.

**Ключевые принципы (подтверждены заказчиком):**
1. **Заявки с сайта** поступают в **LitePMS**, откуда автоматически попадают в **Bitrix24** лидом (через исходящий вебхук LitePMS → адаптер).
2. **Заявки менеджеров** заводятся **и в LitePMS, и в Bitrix24**. Менеджер ведёт лид по воронке в CRM; на стадии **«Бронирование»** выполняет собственно бронирование в LitePMS (вручную в интерфейсе PMS; автоматическое создание брони из лида методом `createBooking` — вне объёма, см. п. 2).
3. **Пока всё остаётся на лидах** (не на сделках и не на контактах/компаниях).
4. **B2C — основная воронка** в Bitrix24; B2B — вторая воронка. Обе ведутся в CRM.
5. **Стадии воронок сопоставимы со статусами LitePMS** (`status_id` 1–9) — прямое соответствие «стадия воронки ↔ статус брони» (см. п. 10.3).

Итоговая цель — единая рабочая картина всех заявок и броней в CRM (лиды) с ведением обеих воронок в Bitrix24 и синхронизацией статусов обратно в LitePMS, плюс сквозная аналитика «реклама/сайт → лид → бронь → оплата».

## 2. Область (scope)

### Входит в объём
- Приём и обработка исходящих вебхуков LitePMS (создание/обновление броней, оплаты, предзаявки).
- Автоматическое создание **лидов в Bitrix24** из заявок сайта (поток LitePMS → CRM) и обновление полей лида по данным брони.
- Ведение обеих воронок (**B2B** и **B2C**, B2C — основная) на **лидах** в Bitrix24.
- Маппинг полей «LitePMS ↔ лид Bitrix24» в обе стороны (см. п. 5).
- Связка «бронь ↔ лид» через внешний идентификатор (`EXT_ID = booking_id`; обратная ссылка `lead_id` — в `client_extradata` брони).
- **Обратная запись статуса** из воронки Bitrix24 в LitePMS через `POST /updateBooking` → `status_id` при достижении пороговых стадий (см. п. 4.2, 7.1).
- Дедупликация, идемпотентность, защита от зацикливания, очередь, ретраи, логирование.
- Передача атрибуции (источник, `ym_clid`/`etext`/`yclid`) в лиды для сквозной аналитики (см. п. 14).

### Вне объёма (на текущем этапе)
- **Автоматическое создание/обновление брони из лида методом `createBooking`** — **не выполняется**. Бронирование выполняет **менеджер вручную в LitePMS** на стадии «Бронирование» (для B2B). Обратно в LitePMS передаётся **только статус** (`updateBooking` → `status_id`) и обратная ссылка `lead_id` (`client_extradata`); коммерческие и клиентские поля брони ведёт LitePMS.
- Работа со **сделками, контактами, компаниями** — **не выполняется**; интеграция ведётся исключительно на **лидах**.
- Полная синхронизация истории БД LitePMS в CRM (одноразовый импорт) — выносится в отдельный этап.
- Доработка самого LitePMS (используется штатный API/вебхуки системы).

## 3. Архитектура

Прокси-приложение (адаптер) на отдельном сервере/хостинге, выступающее посредником между LitePMS и Bitrix24. LitePMS — «движок» бронирования и источник заявок сайта; Bitrix24 — рабочая воронка на лидах (B2B и B2C).

```
                 (исходящие вебхуки, POST)
  Сайт -->  LitePMS  --(webhook)-->  [ Адаптер (наш сервис) ]  --(REST, лиды)-->  Bitrix24
                                                  |   ^                             |
                                                  +---+--------------------------+ |
                                                      |                             |
                          (updateBooking, POST status_id)                       (crm.lead.onUpdate)
                                                      |                             |
                                                      +-----------------------------+
                                              База состояния / очередь / логи
```

> Обмен **двусторонний по статусу**:
> - **Направление A (LitePMS → Bitrix24):** исходящие вебхуки LitePMS создают и обновляют лиды (заявки сайта; заявки менеджеров).
> - **Направление B (Bitrix24 → LitePMS):** обработчик изменения стадии лида в CRM определяет, достиг ли лид пороговой стадии, и через `POST /updateBooking` записывает `status_id` в броню LitePMS (см. п. 4.2, 7.1).
> Остальные поля (даты, суммы, гости) остаются однонаправленными под управлением LitePMS.

### Почему нужен адаптер
- У двух систем разные модели данных и форматы — нужна **трансляция и маппинг**.
- Нужна **связка брони и лида** (ведение пары идентификаторов).
- Нужны **очередь, ретраи, дедупликация и логирование**, которых нет «из коробки».
- Адаптер скрывает от LitePMS особенности REST Bitrix24 и наоборот.

> **Решение принято:** технологический стек адаптера — **PHP** (с REST-клиентом, очередью и фоновыми задачами). Логика настоящего ТЗ от конкретного языка не зависит.

## 4. Потоки данных

### 4.1. Направление A: LitePMS → Bitrix24 (создание и обновление лида)

**Триггеры (события LitePMS):** создание брони (вручную или через модуль бронирования), изменение брони, удаление брони, поступление брони через каналы продаж, онлайн-платёж, предварительная заявка (см. п. 8.3).

**Действия адаптера:**
1. Принять входящий вебхук LitePMS, проверить источник (секрет-заголовок адаптера).
2. Извлечь ключ брони (`booking_id`) и тип события.
3. Определить, существует ли уже сопоставленный лид (по `EXT_ID`, см. п. 6).
4. Если лида нет и событие = создание → **создать лид** (`crm.lead.add`) с маппингом полей; канал/источник определяет, в какую воронку попадает лид (см. п. 10.3).
5. Если лид есть → **обновить поля лида** (`crm.lead.update`), включая стадию по карте статусов, пока лид ведётся автоматически (см. п. 4.2 про «заморозку»).
6. Записать результат в лог и состояние.
7. Передать атрибуцию (`ym_clid`, `etext`, `yclid`, источник) для сквозной аналитики (см. п. 14).

### 4.2. Направление B: Bitrix24 → LitePMS (статус брони при пороге воронки)

По гибридной схеме воронку ведёт **Bitrix24**: сотрудники двигают лиды по стадиям в CRM (обе воронки — B2B и B2C). LitePMS — учётная система броней; движение по воронке и его отражение в статусе брони выполняется так:

- Обработчик события `crm.lead.onUpdate` ловит смену стадии лида.
- Адаптер по `EXT_ID`/`lead_id` находит броню в LitePMS (`client_extradata` хранит `lead_id`).
- По **карте «стадия воронки → status_id»** (см. п. 10.3) определяется соответствие.
- Если стадия достигла **порогового значения** для своей воронки — адаптер вызывает `POST /updateBooking` с новым `status_id`.
- Если `status_id` в LitePMS уже совпадает с изменением из CRM — вызов **не выполняется** (защита от лишних записей и зацикливания, см. п. 9.2).

> **Правило статуса (п. 7.1):** воронку ведёт Bitrix24 с самого начала. Пока лид не достиг пороговой стадии, изменения полей брони из вебхуков LitePMS **могут** двигать лид по воронке автоматически (по прямой карте «status_id → стадия»). После достижения порога лид ведут только сотрудники в CRM вручную, а адаптер **пишет итоговый статус обратно в LitePMS** через `updateBooking`. Точное правило (какие стадии пишутся в LitePMS и для какого диапазона) — согласовывается с заказчиком (см. п. 16).

Из CRM в LitePMS передаётся **только статус** (`updateBooking` → `status_id`); остальные поля брони (даты, суммы, клиент) ведёт LitePMS. Оценка, ответственный менеджер и воронка — атрибуты лида, в LitePMS не передаются.

CRM остаётся **рабочей воронкой** всех заявок и броней на лидах; фактическая учётная обработка (даты, финансы, гости) — в LitePMS; статус согласованно пишется обратно в LitePMS при достижении порогов.

## 6. Связка идентификаторов «бронь ↔ лид»

Чтобы знать, какая бронь соответствует какому лиду, вводится **пара идентификаторов**:
- `LitePMS booking ID` — уникальный ID брони в LitePMS;
- `CRM lead ID` — уникальный ID лида в Bitrix24.

**Правила:**
1. При первом создании лида из брони в поле лида `EXT_ID` (пользовательское поле типа «строка») записывается `booking_id` из LitePMS.
2. При обратном запросе (из LitePMS) поиск лида ведётся по этому полю (`crm.lead.list` с фильтром по `EXT_ID`).
3. Хранение обратной ссылки (`lead_id` в LitePMS) — **выполняется** через REST-метод `POST /updateBooking`: `lead_id` записывается в поле `client_extradata` брони (см. п. 8.4). Это позволяет при изменении стадии лида в CRM (направление B) точно определить броню в LitePMS.
4. Сопоставление считается биективным: одна бронь ↔ один лид.

**Если связка не найдена** — создаётся новый лид (с дополнительными проверками по уникальности, см. п. 9).

## 7. Правила синхронизации и приоритет источника

Чтобы избежать конфликтов, зафиксирована политика «кто главный» по группам полей:

| Группа полей | Источник-владелец | Обоснование |
|--------------|-------------------|-------------|
| Даты заезда/выезда, номер, число гостей | LitePMS | PMS — источник фактического бронирования |
| Финансы (сумма, статус оплаты) | LitePMS (для B2B/B2C — см. ниже) | деньги считаются в PMS; оплаты B2C фиксируются на сайте (аванс) и при заселении |
| Канал/источник | LitePMS | источник брони; определяет воронку (см. п. 10.3) |
| Стадия воронки лида | **Bitrix24 (рабочая воронка)** | лид ведут сотрудники в CRM; при пороге статус пишется обратно в LitePMS |
| Оценка, ответственный менеджер | Bitrix24 | объект CRM, ведётся сотрудниками в CRM |
| Контактные данные гостя | LitePMS (приоритет) | избегаем затирания актуального телефона |

**Порядок по заявкам:**
- **Заявки с сайта** → LitePMS (модуль бронирования) → вебхук → автоматический лид в Bitrix24 (в воронку по источнику).
- **Заявки менеджеров** → заводятся и в LitePMS, и в Bitrix24; менеджер ведёт лид в CRM и на стадии «Бронирование» выполняет бронирование в LitePMS.

### 7.1. Гибридная схема владения статусом (порог записи в LitePMS)

Воронку (обе — B2B и B2C) ведёт **Bitrix24**. LitePMS — учётная система броней, в которую при достижении порога записывается статус. Модель:

**До порога** (лид ещё не достиг целевой стадии воронки):
- движения по воронке задаются **сотрудниками в CRM** (ручная работа менеджера);
- кроме того, вебхуки LitePMS могут автоматически двигать лид по прямой карте «status_id → стадия» (см. п. 10.3), пока лид не достиг порога;
- обратная запись статуса в LitePMS **не выполняется**, пока лид не дошёл до пороговой стадии.

**После порога** (лид достиг пороговой стадии воронки):
- лида ведут **сотрудники в CRM вручную**; адаптер больше **не перезаписывает** стадию лида вебхуками LitePMS («заморозка»);
- при каждом изменении стадии лида после порога адаптер через `POST /updateBooking` **записывает `status_id` обратно в LitePMS** по карте «стадия → status_id» соответствующей воронки (см. п. 10.3);
- сам факт, что статус «заморожен» для вебхуков LitePMS, фиксируется в логе.

**Правила и оговорки:**
1. **Порог необратим:** после его достижения вебхуки LitePMS стадию лида не меняют (защита ручной работы менеджера от «перезаписи» пакетом PMS).
2. **Обратный канал** (`POST /updateBooking`) используется только для `status_id` (и `lead_id` в `client_extradata`); остальные поля брони ведёт LitePMS.
3. **Конфигурация порога:** для каждой воронки задаётся код пороговой целевой стадии (например, для B2B — «Бронирование» или «Заезд»). Точные значения — по результатам согласования (см. п. 16).
4. **Сравнение значений:** адаптер обновляет лид и пишет статус в LitePMS только при фактическом изменении данных; если значение уже совпадает — пропуск (исключает лишние записи и зацикливание, см. п. 9.2).

**Реализация (адаптер), направление A:** перед записью стадии адаптер читает текущего лида (`crm.lead.get`), сверяет достигнутый порог по конфигурации воронки и, если порог пройден, исключает поле стадии из пакета обновления (остальные поля синхронизирует).

**Реализация (адаптер), направление B:** обработчик `crm.lead.onUpdate` ловит смену стадии лида, по `EXT_ID`/`lead_id` находит броню в LitePMS и вызывает `POST /updateBooking` с новым `status_id` (при достижении порога и фактическом изменении).

Оценка и ответственный менеджер всегда ведутся в CRM и никогда не перезаписываются адаптером; в LitePMS они не передаются.

## 8. Техническая реализация каналов

### 8.1. Входящий вебхук Bitrix24 (у заказчика)

Администратор портала выпускает **входящий REST-вебхук** со следующими правами (scope):
- `crm` (обязательно) — для работы с лидами;
- `user` — для получения данных о менеджерах (опционально).

Адаптер хранит URL вебхука как секрет в конфигурации **и не передаёт его никуда**, кроме запросов адаптера к порталу.

**Основные методы (в рамках данного ТЗ):**
- `crm.lead.add` — создание лида;
- `crm.lead.update` — обновление лида (в т.ч. стадии);
- `crm.lead.get` — чтение лида по ID;
- `crm.lead.list` — поиск лидов (по `EXT_ID`, по контактам);
- `crm.lead.fields` — получение перечня и кодов полей лида (для проверки маппинга).

### 8.2. Исходящий вебхук (обработчик событий) Bitrix24

Обработчик события `crm.lead.onUpdate` — ядро направления B (рабочая воронка): при смене стадии лида адаптер определяет бронь по `EXT_ID`/`lead_id` и, если лид достиг пороговой стадии своей воронки, вызывает `POST /updateBooking` с новым `status_id` (см. п. 4.2, 7.1). Функция включается конфигурацией (per-funnel). `crm.lead.onAdd` в схеме используется только для фиксации `lead_id` — лид не создаёт броню автоматически.

### 8.3. Каналы и API LitePMS (исходящие вебхуки)

Документация Lite PMS предоставлена заказчиком.

- **API-ключ** (`login` + `hash`) обязателен для обращений к REST-API; доступен на тарифе **Business**.
- Webhook-уведомления отправляются на указанный в настройках адрес **методом POST**.
- Если адрес недоступен (сервер не возвращает код `200`) — уведомления **могут быть заблокированы**. Это обязательное требование к надёжности endpoint адаптера (см. п. 12).
- **Подпись/секрет вебхука не предусмотрена** (HMAC нет). Endpoint адаптера должен быть на секретном, непубликуемом адресе и дополнительно проверять источник по фиксированному секретному заголовку (см. п. 11).
- **Лимиты запросов (rate limits) документацией не установлены.**

#### 8.3.1. Подтверждённая конфигурация webhook-уведомлений

- Уведомления **включены** (`да`).
- Адрес для уведомлений: `https://avshotel.ru/include/...php` (секретный, непубликуемый; на время согласования — временный, до фактического развёртывания эндпоинта на `libre.na4u.ru`).

## 8.4. REST-API LitePMS (направление B и чтение броней)

У LitePMS **есть** HTTP REST-API (базовый адрес — `https://litepms.ru/api`, подтверждён заказчиком). Авторизация — параметры **`login`** и **`hash`** (API-ключ) в строке запроса (query). Доступен на тарифе **Business**.

Доступные методы:

| Метод | Тип | Назначение |
|-------|-----|------------|
| `/getBookingFields` | GET | поля, используемые в бронировании |
| `/getBookings` | GET | информация о всех бронированиях |
| `/getBooking` | GET | информация о конкретном бронировании |
| `/createBooking` | POST | создание бронирования (**вне объёма** данного ТЗ) |
| `/updateBooking` | POST | **обновление брони и клиента (в т.ч. статуса)** — обратный канал направления B |
| `/getBookingServices` | GET | услуги конкретного бронирования |
| `/addBookingService` | POST | добавление услуги к бронированию |
| `/searchBooking` | POST | поиск броней по параметрам |

**Метод `POST /updateBooking`** — обратный канал для статуса (направление B). Формат — `application/x-www-form-urlencoded`, обязательный параметр **`id`** (ID брони). Ключевые поля:

| Параметр | Описание |
|----------|----------|
| `id` *(обязателен)* | ID брони |
| `status_id` | Статус брони: 1 — не подтверждено, 2 — подтверждено, 3 — отменено, 4 — выезд, 5 — незаезд, 6 — проживание, 8 — резерв, 9 — overbooking |
| `client_extradata` | Доп. данные клиента — используется адаптером для хранения `lead_id` (см. п. 6) |
| `date_in`, `date_out`, `time_in`, `time_out`, `person`, `person_add`, `room_id`, `bed_id`, `is_bed`, `price`, `stayprice`, `stayprice_type`, `rate_id`, `label_id`, `service_id`, `service_number` | Параметры брони (в рамках ТЗ адаптер их **не** передаёт — ведёт LitePMS) |

| `comment`, `client_booking_comment` | Комментарии (в рамках ТЗ адаптер их **не** передаёт) |

Ответ успешного запроса — `{"success": true}`.

> **Важно:** адаптер использует `updateBooking` **только** для записи статуса (`status_id`) и сохранения обратной ссылки `lead_id` (`client_extradata`). Остальные поля брони остаются под управлением LitePMS (см. п. 4.2, 7.1).

## 9. Дедупликация, идемпотентность и защита от зацикливания

### 9.1. Идемпотентность
Каждое событие обрабатывается **ровно один раз** на уровне приложения:
- адаптер хранит `event_id`/хэш полученного сообщения и не обрабатывает повторно уже обработанное (`idempotency key`);
- все запросы к Bitrix24 (создание лида) защищены от дублей проверкой `EXT_ID` перед созданием.

### 9.2. Защита от зацикливания «пинг-понга»
Типичная проблема двусторонней синхронизации — бесконечный обмен уведомлениями, когда изменение из системы A вызывает событие в системе B, которое снова уходит в A.

**Меры:**
1. **Тэг происхождения:** при записи поля в одной системе, сделанной самим адаптером, проставляется служебная пометка, а обработчик `onUpdate` игнорирует события, порождённые самим адаптером.
2. **Сравнение значений:** обработчик обновляет объект только при фактическом изменении данных («поле уже равно значению — пропускаем»).
3. **Глубина/флаг обработки:** признак «последняя запись сделана адаптером» хранится в состоянии.
4. **Обратный канал (направление B):** запись статуса в LitePMS через `updateBooking` не порождает обработчика «ответа»; повторный вебхук изменённой брони с совпадающим `status_id` игнорируется по правилу «сравнения значений» (см. также п. 7.1).

### 9.3. Дедупликация лидов
Перед созданием нового лида из брони выполняются проверки:
- поиск по `EXT_ID` (та же бронь) — если найден, обновляем, а не создаём;
- при отсутствии `EXT_ID` — поиск по телефону/email гостя + датам (эвристика) с выводом в лог возможного дубля.

## 10. Обработка ошибок, очередь и логирование

### 10.1. Очередь и повторные попытки
- Каждое событие помещается в **очередь** (постоянное хранилище).
- При недоступности Bitrix24/LitePMS или ошибке — **повторные попытки** с экспоненциальным ростом интервала, до максимального числа.
- SLA: задержка от события до отражения в другой системе — **не более 5 минут** (воркер запускается раз в минуту по cron).

### 10.2. Логирование
- Журнал по каждому событию: приём вебхука, сопоставление пары, результат записи в CRM/LitePMS, ошибки, ретраи.
- **Маскирование персональных данных** (телефоны/email логируются частично или маскируются).
- Отчётность по синхронизации выгружается в формате **XLS** по периодам.

### 10.3. Справочники статусов (прямое соответствие стадия ↔ статус)

В Bitrix24 используются **две воронки на лидах**: **B2C (Частные) — основная** и **B2B**. Признак разделения задаётся по справочнику источников LitePMS: «Групповой заезд» → воронка B2B; «Индивидуальный заезд», «Блоггеры» → воронка Частных (B2C); **по умолчанию** все брони — в Частные (B2C).

Стадии воронок **сопоставимы со статусами LitePMS** (`status_id` 1–9) — прямое соответствие «стадия воронки ↔ статус брони», по каждой воронке отдельно.

**Воронка B2B** (источник «Групповой заезд»):

| `status_id` LitePMS | Стадия воронки Bitrix24 |
|---------------------|--------------------------|
| 1 — не подтверждено | Разобрать / Первичный звонок / Разговор с ЛПР / КП / Звонок и ОС / Встреча |
| 2 — подтверждено | Бронирование / Договор+Счет / Авансы / Корректировка количества / Расчет |
| 6 — проживание | Заезд |
| 4 — выезд | Акты и ОС / Сделка успешна |
| 5 — незаезд | Сделка провалена |
| 3 — отменено | Сделка провалена |
| 8 — резерв | *(стадия не меняется)* |
| 9 — overbooking | Сделка провалена |

**Воронка B2C (Частные) — основная** (источники «Индивидуальный заезд», «Блоггеры», по умолчанию — все брони):

| `status_id` LitePMS | Стадия воронки Bitrix24 |
|---------------------|--------------------------|
| 1 — не подтверждено | Новая / Подготовка документов / Счёт на предоплату / В работе |
| 2 — подтверждено | Финальный счёт |
| 6 — проживание | Сделка успешна |
| 4 — выезд | Сделка успешна |
| 5 — незаезд | Сделка провалена |
| 3 — отменено | Сделка провалена |
| 8 — резерв | *(стадия не меняется)* |
| 9 — overbooking | Сделка провалена |

**Двойная карта (в оба направления):**
- **Прямая (A):** «status_id → стадия воронки» — используется адаптером при вебхуках LitePMS для движения лида по воронке до порога (по воронке, выбранной по источнику).
- **Обратная (B):** «стадия воронки → status_id» — инверсия прямой карты, по каждой воронке отдельно; используется адаптером при изменении стадии лида после порога для записи статуса в LitePMS (см. п. 7.1).

**Порог записи в LitePMS:** указывается для каждой воронки отдельно (например, для B2B — достижение стадии «Бронирование» или «Заезд»; точное значение подтверждается заказчиком). До порога лид может двигаться вебхуками LitePMS по прямой карте; после порога стадию ведут только в CRM, и адаптер пишет `status_id` в LitePMS (см. п. 7.1).

**Парное правило по оплате:** событие `booking_module_payment` не двигает стадию воронки, а отражается в полях оплаты лида (сумма, дата, статус оплаты). Схема оплат (см. п. 13):
- **B2C:** аванс — на сайте (через модуль бронирования / ссылку онлайн-оплаты), окончательная оплата — **при заселении**;
- **B2B:** оплата **по ссылке на онлайн-оплату счёта** и **по счёту** (договор + счёт), обработка в Bitrix24.

## 11. Безопасность

- Обмен только по **HTTPS**.
- **Секреты** (токен входящего вебхука Bitrix24, API-ключ LitePMS `login`/`hash`, секрет заголовка) хранятся в защищённом конфиге/хранилище секретов и **никогда** не попадают в код, логи или репозиторий.
- **Вебхуки LitePMS не подписываются** (HMAC не предусмотрен): endpoint адаптера — на секретном, непубликуемом адресе, принимает только от настроенного источника и дополнительно проверяет источник по фиксированному секретному заголовку (см. п. 8.3).
- Обработчик Bitrix24: при возможности — проверка подписи события.
- Валидация и санитизация всех входящих данных (защита от инъекций и некорректного payload).
- Разграничение прав: приложению выдаётся минимально необходимый скоуп.

## 13. Сценарии и приёмочные критерии

### 13.1. Ключевые сценарии для проверки
1. **Заявка с сайта** → LitePMS (модуль бронирования) → вебхук → **автоматически создан лид** в Bitrix24 в воронку по источнику (`EXT_ID = booking_id`), атрибуция передана.
2. **Заявка менеджера** → создаётся и в LitePMS, и в Bitrix24 (лид); менеджер ведёт лид по воронке в CRM.
3. **Бронирование на стадии «Бронирование» (B2B):** менеджер на стадии «Бронирование» воронки выполняет бронирование в LitePMS (вручную в UI PMS); лид по этой стадии не создаёт бронь автоматически (`createBooking` вне объёма, см. п. 2).
4. **Движение по воронке в Bitrix24:** при смене стадии лида в CRM адаптер по обратной карте «стадия → status_id» определяет статус; при достижении порога вызывает `POST /updateBooking` и пишет `status_id` в LitePMS.
5. **Вебхук LitePMS до порога** двигает лид по прямой карте «status_id → стадия» (пока лид не достиг порога).
6. **Вебхук LitePMS после порога** не перезаписывает стадию лида («заморозка»), но остальные поля (даты, сумма, оплата, атрибуция, комментарий) обновляются.
7. **Ручная работа менеджера в CRM:** перевод лида менеджером в любую стадию после порога сохраняется и не откатывается при поступлении вебхука LitePMS.
8. **Оплата B2C:** аванс — на сайте (событие `booking_module_payment` отражается в поле оплаты лида, стадию не двигает); окончательная оплата при заселении.
9. **Оплата B2B:** оплата по ссылке онлайн-оплаты счёта (`invoice_hash`) и по счёту (договор + счёт); обработка в Bitrix24.
10. **Дубль вебхука** (повтор события) → не создаёт второй лид и не накапливает дубли.
11. **Разрыв сети/ошибка** → событие уходит в очередь и повторяется, система приходит в консистентное состояние.
12. **Расхождение статусов:** до порога синхронизированы; после порога статус ведёт CRM, при достижении пороговых стадий пишется в LitePMS. Если обратная запись отключена/не согласована для воронки — расхождение не считается ошибкой, фиксируется в логе.

### 13.2. Критерии приёмки
- Все сценарии п. 13.1 выполняются без ручного вмешательства.
- Максимальная задержка синхронизации (от события до отражения в другой системе) — **не более 5 минут** (SLA).
- Лог по каждому событию доступен и читаем.
- Секреты не появляются в логировании.
- Документация по маппингу и запуску системы в комплекте.

## 14. Сквозная аналитика в Bitrix24

Сквозная аналитика показывает **полный путь клиента** — от клика по рекламному объявлению до брони и оплаты — и позволяет рассчитывать стоимость привлечения клиента и ROI по каналам. В рамках интеграции: атрибуция «реклама/сайт → лид → бронь → оплата».

### 14.1. Требование к тарифу
- Функция доступна не на всех тарифах. Необходимо подтвердить её наличие на текущем тарифе портала администратором.

### 14.2. Настройка в Bitrix24 (администратором портала)
- Подключение источников трафика (CRM → Аналитика → Сквозная аналитика → Настройки подключения → Подключение источников трафика) и задание UTM-меток.
- Распределение телефонов и e-mail для атрибуции заявок по источникам (при необходимости).
- Отчёты (CRM → Аналитика → Сквозная аналитика).

### 14.3. Требования к адаптеру
- При создании/обновлении лида из брони адаптер передаёт **источник/канал брони** в `SOURCE_ID` и выбирает воронку (B2B/B2C, см. п. 10.3).
- Атрибуционные параметры вебхука `ym_clid`, `etext`, `yclid` передаются в пользовательские поля лида (UTM/tracking), формируя корректный «Путь клиента».
- Конверсия учитывает переход брони в **оплату**: фиксируются момент и сумма оплаты (событие `booking_module_payment`; связка по `EXT_ID`, см. п. 7 и 10.3). Для B2C — аванс на сайте + окончательная оплата при заселении; для B2B — оплата по ссылке/счёту.
- Если источник не распознан — логируется как «без источника» для ручного маппинга.

### 14.4. Критерий приёмки
- В отчётах сквозной аналитики прослеживается атрибуция «источник → лид → бронь → оплата», доступны стоимость привлечения и ROI по каналам.

## 15. Этапы разработки

1. **Сбор входных данных:** документация LitePMS (вебхуки, REST-API, статусы), фактические коды полей лида и UF портала.
2. **Согласование маппинга**, политики владения полями и справочников статусов **обеих воронок** (особенно воронки B2C как основной).
3. **Каркас адаптера:** приём вебхуков, очередь, логирование, связка идентификаторов.
4. **Направление A** (LitePMS → лид): автосоздание лидов из заявок сайта, обновление полей, атрибуция; тесты на тестовых бронях.
5. **Ведение воронок в Bitrix24 на лидах** (B2B и B2C), в т.ч. автоматическое движение по прямой карте статусов до порога.
6. **Направление B по статусу:** обработчик `crm.lead.onUpdate` + запись `status_id` в LitePMS через `POST /updateBooking` при достижении пороговых стадий (см. п. 4.2, 7.1, 8.4).
7. **Сквозная аналитика:** настройка источников трафика в Bitrix24 и передача атрибуции из адаптера (см. п. 14).
8. **Обработка ошибок, ретраи, защита от зацикливания.**
9. **Тестирование сценариев (п. 13) и приёмка.**
10. **Развёртывание, мониторинг, документация.**

## 16. Что требуется от заказчика для продолжения

1. Документация и формат уведомлений **LitePMS** получены; подтверждены отсутствие подписи (HMAC) и отсутствие rate limits. REST-API LitePMS **есть** (`POST /updateBooking`, см. п. 8.4). **Осталось подтвердить:** фактический **URL входящего REST-вебхука Bitrix24** и реальные значения **`login`/`hash`** LitePMS (заказчик хранит их секретно; адаптеру они передаются на этапе внедрения в защищённом конфиге).
2. **Точные пороговые стадии** для каждой воронки (после каких стадий адаптер пишет `status_id` обратно в LitePMS) и подтверждение карт «стадия → status_id» (для B2B и для B2C).
3. Подтверждение справочника источников: маппинг «Групповой заезд / Индивидуальный заезд / Блоггеры» и других «Источников бронирования» LitePMS → источники лидов и воронки в CRM.
4. Перечень фактических **полей и пользовательских полей лида** на портале (нужно для точного маппинга).
5. Информация о серверной среде для развёртывания адаптера (частично уточнено: `libre.na4u.ru`, docroot `www/`, PHP/8.3.14).
6. Подтверждение наличия **сквозной аналитики** на тарифе портала и список рекламных источников для подключения в Bitrix24 (для п. 14).

## 17. Принятые решения (закрытые вопросы)

| Вопрос | Решение |
|--------|---------|
| Технологический стек адаптера | **PHP** |
| Политика владения полями (п. 7) | **подтверждена** |
| Роль CRM | **рабочая воронка на лидах** (обе воронки — B2B и B2C); учётная обработка броней — в LitePMS |
| Объект интеграции в CRM | **лиды** (не сделки, не контакты/компании) |
| Основная воронка | **B2C (Частные)**; B2B — вторая воронка |
| Владение статусом (п. 7.1) | **воронку ведёт Bitrix24**; при достижении пороговых стадий адаптер пишет `status_id` обратно в LitePMS через `POST /updateBooking` |
| Направление B (лид → LitePMS) | **только статус** через `POST /updateBooking` (+ `lead_id` в `client_extradata`); остальные поля не передаются |
| Автосоздание/обновление брони из лида | **не выполняется** (`createBooking` вне объёма); бронирование выполняет менеджер вручную в LitePMS на стадии «Бронирование» |
| Заявки с сайта | LitePMS → вебхук → автоматический лид в Bitrix24 |
| Заявки менеджеров | заводятся и в LitePMS, и в Bitrix24 |
| Оплата B2C | аванс на сайте, окончательная оплата при заселении |
| Оплата B2B | по ссылке онлайн-оплаты и по счёту; обработка в Bitrix24 |
| Формат отчётности/логов | **XLS** |
| SLA задержки синхронизации | **не более 5 минут** |
| Подпись/секрет вебхука LitePMS (HMAC) | **не предусмотрена** — безопасность на стороне адаптера (п. 8.3, 11) |
| Лимиты запросов LitePMS (rate limits) | **не установлены** |
| Форматы уведомлений LitePMS (п. 8.3.3–8.3.5) | **зафиксированы** (бронь / оплата / предзаявка) |
| Воронки сегментации (п. 10.3) | **две:** Частные (B2C) — основная, и B2B; признак — справочник источников LitePMS («Групповой заезд» → B2B, остальное → Частные, по умолчанию Частные) |
